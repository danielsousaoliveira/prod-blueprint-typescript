End-to-end technical blueprint

Doctor Appointment Scheduling System

One NestJS process serving REST and GraphQL over MongoDB and Redis, with in-process BullMQ workers and a transactional outbox. Two correctness properties drive every structural decision: no double-booking under concurrency, and timezone arithmetic that survives DST.

The single most important structural fact

There is one deployable. The HTTP API, the GraphQL server, the BullMQ notification worker and the outbox relay poller all run inside the same Node process, wired by the same Nest DI container. Scaling the API scales the workers. This is a deliberate trade — it removes a deployment unit at the cost of coupling their scaling — and it is the first thing a senior interviewer will probe.

Notification provider The only external dependency. Abstracted behind a port so the e2e suite can intercept it with MSW inside the API process. Worker — 5xx/429 marked retryable; job retried by BullMQ

The one annotation people miss

run.googleapis.com/cpu-throttling: 'false'. Cloud Run throttles CPU outside a request by default. The outbox relay polls on a timer and the BullMQ worker processes jobs between requests — with throttling on, they'd only run while a request happened to be in flight. The symptom is "notifications arrive in bursts whenever someone loads a page", which is not an error and therefore expensive to diagnose.

Counter-proposal accepted by the patient

Patient → click "Accept 10:30" → POST /v1/appointments/{id}/patient-accept Cookie: sid → AuthGuard → actor {role: patient, profileId: patient-1} → AppointmentService.applyEvent → repository.findById [Mongo appointments] → transition(current, {type:'patientAccept'}, actor) → isParty? patientId === actor.profileId, else NOT_A_PARTY → 404 → COUNTER_PROPOSED allows patientAccept for role patient? yes → returns ConfirmedAppointment{ confirmedSlot = proposedSlot } → repository.update(next, expectedStatus='COUNTER_PROPOSED') → findOneAndReplace({_id, status: expected}) ← optimistic concurrency → insertMany(outbox: appointment.confirmed) ← same transaction → cache.invalidate(doctorId) [Redis INCR avail-version] → 200 AppointmentDto{ status: CONFIRMED, startsAt = proposed } → invalidate calendar → GraphQL refetch → both parties' views converge on next poll
Why the DTO differs from the domain model

The domain is a discriminated union — proposedSlot is non-optional on COUNTER_PROPOSED and does not exist on the other variants, so "a counter-proposal with no proposed time" is unrepresentable. The wire DTO flattens this into nullable fields, because clients want a stable shape. Both mappings live in one place per surface: toAppointmentDto for REST, toGql for GraphQL.

Plate 06 — module import order. Order matters: AuthModule registers the global guard, so everything after it is protected by default.

Auth

Purpose: establish identity and enforce that authorization is a domain rule, not a controller concern. Inputs: email/password, session cookie. Outputs: Actor {userId, role, profileId}. Dependencies: Redis, Mongo users, argon2.

  • Sessions over JWT. Opaque 256-bit ids in Redis. Consequences: instant revocation, no signing secret to rotate or leak, and a Redis round trip on every request. The stored key is sha256(sid) — a Redis dump or a leaked key listing does not yield usable session tokens.
  • Two rate-limit counters. Per-email alone enables a lockout attack against a known user; per-IP alone misses password spraying. Per-IP is looser because offices and carriers share addresses. Both keys are hashed, so the store holds no PII.
  • Timing. A missing user still costs an argon2 verify against a cached dummy hash, so response time doesn't reveal account existence. The rate limiter runs first, so an attacker can't spend the server's CPU on every attempt.
  • Session fixation is structurally impossible — there is no pre-auth session to upgrade, and login always mints a fresh id.
  • Bottleneck: argon2id at 19 MiB / t=2 is ~50ms of CPU per login. On a 1-vCPU instance with concurrency 80, a login burst is the CPU ceiling. Scaling: logins are rare relative to reads; if it mattered, move auth to its own service or raise maxScale.
  • Monitoring: currently only request logs. Missing: a counter on 401/429 rates, which is the actual attack signal.

Appointments

Purpose: the booking lifecycle. The state machine is the heart of the system and is worth being able to draw from memory.

Plate 06b — the transition table. Each edge is also keyed by role: a patient cannot accept, a doctor cannot patientAccept.

  • The table is as const satisfies { [S in Status]: { [P in Party]: readonly EventsForParty<S,P>[] } } — the runtime table and the compile-time type are checked against each other, so they cannot drift.
  • Three refusal reasons, deliberately distinct: NOT_A_PARTY → 404 (not 403 — a 403 confirms the appointment exists, which is an enumeration oracle); ACTOR_NOT_PERMITTED → 403; ILLEGAL_TRANSITION → 409.
  • Two layers of concurrency control. The Redis lock is the cheap first line, turning most races into a fast 409. The partial unique index is the guarantee — it holds even if Redis is down, the lock TTL expires mid-request, or two instances race. Updates additionally use findOneAndReplace({_id, status: expected}) as optimistic concurrency, so two doctors clicking Accept simultaneously produce one success and one 409.
  • Why the index is partial: filtered to REQUESTED | COUNTER_PROPOSED | CONFIRMED. Without the filter, a cancelled 09:00 slot could never be rebooked. This is also why Cosmos DB's Mongo API is not a drop-in — it doesn't support partial indexes, so migrating clouds would be a redesign of the correctness mechanism, not a config change.
  • Bottleneck: lock contention is per (doctorId, startsAt), so it only serialises genuine conflicts. Failure: a crash between commit and cache invalidation leaves stale availability for ≤60s.

Availability

Purpose: compute bookable slots from recurring rules, minus exceptions, minus held slots. Pure function at the core — computeAvailability does zero I/O, which is why 165 unit tests can cover DST behaviour with no database.

  • Pipeline: expandRules → mergeIntervals → subtractIntervals → chopIntoSlots.
  • DST handling. Rules are stored as wall-clock time plus an IANA zone, never an offset. Expansion steps plus({days: 1}) rather than adding 24 hours, because a local day is 23 or 25 hours across a transition. Non-existent local times (spring forward) are skipped by default, with an opt-in shift policy; ambiguous times (fall back) resolve to the first occurrence, and that choice is asserted in a test so a Luxon upgrade can't change it silently. On a fall-back day a 09:00–13:00 block is genuinely five real hours — the arithmetic gets that right for free because it works on instants.
  • Cache: versioned keys, 60s TTL. Invalidation is INCR on a version counter — old entries become unreachable instantly and expire naturally. No SCAN, no delete storm, and it's safe under concurrency.
  • Bottleneck: a wide range with many rules is O(rules × days). Capped at 90 days by the request schema. Failure: cache errors are caught and logged; the system degrades to always computing.

Outbox & Jobs

  • The problem it solves: writing to the database and publishing to a queue are two systems. Do them separately and a crash between them either loses the notification or sends one for a booking that rolled back. The outbox row is written in the same Mongo transaction as the appointment, so the two facts commit together.
  • At-least-once, deduplicated twice. The relay claims with a 30s TTL and marks published after enqueueing — a crash in between means a re-send. BullMQ's jobId = messageId and the provider's Idempotency-Key both absorb it.
  • Cleanup: a TTL index on publishedAtDate drops published rows after 7 days, so the collection doesn't grow without bound.
  • Bottleneck: claimUnpublished issues one findOneAndUpdate per message — 50 round trips per tick. Fine at this volume; the fix at scale is a bulk claim with a claim token.
  • Scaling: multiple instances run the relay concurrently and that is safe — the claim is atomic. Throughput scales with instance count, which is a happy accident of the single-deployable design rather than a plan.

GraphQL

  • Why both surfaces: the calendar view needs availability + appointments + doctor details in one round trip — that's a GraphQL query. Booking and transitions are commands with idempotency semantics and RFC 7807 errors — those are REST. The frontend genuinely uses both.
  • Guards, because the client composes the query: depth limit 7 (custom validation rule, handles fragment cycles), complexity limit 1000 (Apollo plugin, rejected at didResolveOperation — before any resolver runs). Introspection off in production.
  • N+1: DataLoader per request batches doctor/patient lookups into one $in query. There's a QueryCounter on the repositories specifically so a test can assert the real round-trip count.
  • Authorization is not duplicated. Both surfaces call the same AppointmentService, and the state machine does the checking. appointments takes no doctorId argument — the server scopes it to the session, so passing one is now a schema validation error rather than a silently-ignored filter.
  • autoSchemaFile: true in production (in-memory) rather than a file path, because Cloud Run's filesystem is read-only and a non-root user can't write schema.gql. This was a real bug caught by running the image in CI, not by any test.

Two details worth volunteering unprompted

CMD is node, not npm start. npm sits between the init process and node and does not forward SIGTERM to its child, so the graceful shutdown handler would never run and every deploy would kill in-flight requests. That one line is what makes all the draining logic in main.ts actually reachable — and CI asserts it by running docker stop -t 15 and grepping the logs for drained cleanly plus exit code 0.

Migrations run before the new revision, as a job, never at boot. Several instances starting at once would race each other. That ordering only works because every migration is backwards-compatible with the currently-running code — during a rollout both versions serve traffic. Destructive changes go in release N+1.

Security posture

  • Transport: TLS terminated at Cloud Run; datastores on private IPs, never publicly routable. Container runs as non-root node, asserted in CI.
  • Session: HttpOnly (no JS access), SameSite=Lax, Secure by default — the flag defaults to the safe direction and an environment that needs it off must say so explicitly. Ids are hashed at rest in Redis.
  • CSRF: SameSite=Lax is the primary control; the Origin and Sec-Fetch-Site checks are defence in depth. ALLOWED_ORIGINS never defaults to permissive — a security control that's off until someone remembers to turn it on isn't a control.
  • Passwords: argon2id, 19 MiB / t=2 / p=1, at the OWASP floor. needsRehash exists so parameters can be raised later.
  • Secrets: referenced from Secret Manager, never inlined — a connection string in YAML is a connection string in git history, and rotating it becomes a commit. CI authenticates via Workload Identity Federation, because a key that never expires is a key that eventually leaks.
  • Information disclosure: unhandled exceptions log the detail and return a bare 500. Not-a-party returns 404, not 403. Login returns the same message and takes the same time whether or not the account exists.
  • Supply chain: npm ci everywhere, so no build ever resolves a dependency tree that wasn't reviewed. Multi-stage build ships no compiler, no dev dependencies, no source.
  • Gaps I'd name before being asked: no WAF or network-level rate limiting; no audit log of who changed which appointment; no secret rotation schedule; nothing enforces password strength on registration (there is no registration flow yet).

Observability

  • Have: structured Pino JSON that Cloud Logging parses natively; authorization and cookie redacted; /health excluded from request logging so probes don't bury real traffic; a readiness endpoint that reports per-dependency status and latency.
  • Missing, in priority order: (1) a request id propagated into every log line and returned in the problem+json body, so a user-reported error maps to a server log entry — this is the highest-leverage missing piece; (2) uptime checks alerting on /health rather than raw error rate, because readiness fails before users notice; (3) queue depth and outbox lag metrics, which are the only signals that would catch a stalled relay; (4) distributed tracing.

Interview walkthrough

Spoken, start to finish, to a Senior Staff Engineer. Roughly twelve minutes at a normal pace. Lead with the invariants — the architecture is downstream of them.

1 · Open with the problem, not the stack

"It's a doctor appointment scheduler. A patient requests a slot, the doctor accepts, declines, or proposes a different time, and the patient accepts or declines that. Either side can cancel, and everyone gets notified.

Two properties drove every structural decision. First: no double-booking, ever, including two requests in the same millisecond. Second: correct timezone handling — doctors and patients in different zones, with recurring availability that survives daylight-saving transitions without silently shifting. Nearly everything else in the design follows from those two."

2 · The shape

"One deployable: a Node 22 process running NestJS. It serves REST at /v1 and GraphQL at /graphql, and it also hosts a BullMQ worker and an outbox relay poller. Behind it, MongoDB as the system of record and Redis doing six different jobs. The frontend is a React 19 SPA with TanStack Query, served same-origin — Vite's proxy in development, Cloud Run in production — so cookie behaviour in dev matches production exactly.

Internally it's hexagonal: api is transport, application orchestrates, domain is pure with zero I/O, persistence holds adapters injected behind Symbol tokens. That layering is what makes 165 unit tests possible with no database — the interval algebra, the DST expansion, and the state machine are all pure functions."

3 · The double-booking guarantee — lead with this

"The guarantee lives in the database, not in application code. There's a partial unique index on (doctorId, startsAt), filtered to the active statuses. Partial matters: without the filter a cancelled 09:00 slot could never be rebooked.

In front of that there's a Redis lock keyed on doctor and slot start, but I'd call that an optimisation, not the guarantee. It turns most races into a fast 409 instead of a wasted transaction. If Redis is down, both requests reach Mongo and the second gets a duplicate-key error, which the adapter translates into SlotTakenError and then a 409. Same outcome, different path.

State transitions add a third layer: findOneAndReplace guarded on the expected status, which is optimistic concurrency. Two doctors clicking Accept at once produce one 200 and one 409.

The e2e suite proves this with two real browser contexts hitting the same slot — I wanted evidence, not an argument."

4 · Timezones

"Availability is stored as recurring rules: weekday plus wall-clock time plus an IANA zone. Never an offset — an offset is a fact about a moment, not about a clinic.

Expansion steps day by day with Luxon's plus({days: 1}), not by adding 24 hours, because a local day is 23 or 25 hours across a transition. Non-existent times on spring-forward are skipped by default, with an opt-in shift policy. Ambiguous times on fall-back resolve to the first occurrence, and I assert that in a test so a library upgrade can't change it silently.

There's a nice consequence: on a fall-back day, a 09:00–13:00 block really is five hours of real time. The arithmetic gets that right for free, because it works on instants rather than wall-clock durations.

The e2e suite pins the browser to America/New_York while the clinic is in Europe/Lisbon, so every test exercises the cross-timezone path rather than the trivial same-zone case."

5 · Authorization as a domain rule

"Authorization isn't a controller concern here. The state machine decides both which transitions are legal and which party may make them — a patient can't accept, a doctor can't patientAccept. The transition table is declared once as a const that must satisfy a mapped type, so the runtime table and the compile-time type can't drift.

That's why both REST and GraphQL enforce identical rules with zero duplication: they both call the same service, and the domain does the checking.

One deliberate detail: 'you're not a party to this appointment' returns 404, not 403. A 403 confirms the appointment exists, which is an enumeration oracle."

6 · Sessions over JWT

"Opaque 256-bit random ids stored in Redis, keyed by their SHA-256 hash. Three reasons over a JWT: instant revocation; no signing secret to manage, and a secret that exists is a secret that can leak; and the cookie can be unsigned, because a tampered value simply fails to resolve.

The cost is a Redis round trip per request. At this scale that's the right trade — I'd revisit it if the session store became a hot path across many services.

The login path has three details I'd want to be asked about: rate limiting runs first, before any expensive work, so an attacker can't spend our CPU on every attempt. A missing user still costs a full argon2 verify against a cached dummy hash, so timing doesn't reveal account existence. And there are two rate-limit counters — per-email alone lets you lock a known user out, per-IP alone misses password spraying, and per-IP is looser because offices share addresses.

Session fixation is structurally impossible: there's no pre-auth session to upgrade, and login always mints a fresh id."

7 · Why both REST and GraphQL

"Not for the sake of it. The calendar view needs availability, appointments, and doctor details in one round trip — that's genuinely a GraphQL query, and the frontend uses it. Booking and transitions are commands with idempotency keys and RFC 7807 errors — those are REST.

GraphQL gets guards because the client composes the query: depth limit 7, complexity limit 1000 rejected before any resolver runs, introspection off in production, and DataLoader per request to kill N+1. There's a query counter on the repositories specifically so a test can assert the real round-trip count rather than trusting that batching works."

8 · The outbox — the async story

"Writing to the database and publishing to a queue are two systems. Do them separately and a crash in between either loses the notification or sends one for a booking that rolled back.

So the outbox row is written in the same Mongo transaction as the appointment. That's also why Mongo runs as a replica set even locally — multi-document transactions need one.

A poller claims batches with a 30-second lease and enqueues to BullMQ. Delivery is at-least-once and deduplicated twice: BullMQ's jobId is the message id, and the provider gets an Idempotency-Key. Published rows are cleaned up by a TTL index after seven days.

The relay is safe to run on every instance concurrently because the claim is atomic — which is a happy consequence of the single-deployable design rather than something I planned."

9 · Deployment

"CI is seven jobs. Lint and typecheck are separate so a type error and a lint error both get reported in one run instead of the second hiding behind the first. Integration tests use Testcontainers on random ports so they're safe alongside other jobs. E2E brings up real Mongo and Redis with --wait so Playwright never races a replica set that's still electing a primary.

The build job verifies the image, not just that it compiled — it asserts the container runs as non-root, that it boots and answers /health, and that docker stop produces a clean drain with exit 0. Two real bugs came out of that: msw being statically imported and pruned in production so the image crashed on boot, and GraphQL writing schema.gql at startup, which fails for a non-root user on a read-only filesystem. Neither was caught by any test — only by running the container.

Publishing is gated on everything and only from main.

In production it's Cloud Run: min 1 instance so nobody pays for a cold start, max 10 so a traffic spike can't open unbounded Mongo connections — a hundred instances times a pool size is how a serverless autoscaler takes down the database it depends on. All egress goes through a VPC connector so the datastores are on private IPs.

The annotation I'd flag is cpu-throttling: false. Cloud Run throttles CPU outside a request by default, and my relay and worker run between requests. With throttling on, notifications arrive in bursts whenever someone loads a page — not an error, which is what makes it expensive to find.

Migrations run before the new revision, as a job, never on boot. Several instances starting at once would race. That only works because every migration is backwards-compatible with the running code — add in release N, remove in N+1."

10 · Where it breaks, and what I'd do first

"Four things, in the order I'd fix them.

The workers share the API's process. That's the one I'd change first: split them into a second Cloud Run service from the same image with a worker-only entrypoint. Right now a notification backlog can only be cleared by scaling the API, and a slow provider consumes CPU that requests need.

No request-id correlation. Pino emits JSON that Cloud Logging parses, but there's no id threaded through logs and returned in the error body, so a user-reported error can't be mapped to a server log line. That's the highest-leverage missing observability piece, and it's small.

Redis is a single point of failure for sessions. Lose it and everyone is logged out. HA tier, and I'd split the queue instance from the session instance so a queue backlog can't evict sessions.

Availability compute is O(rules × days) on a cold cache. Bounded today by a 90-day cap in the request schema and a 60-second cache. At scale I'd precompute per doctor-week in a job — and because the engine is already a pure function, that's a caching change, not a rewrite.

And one thing I'd name before being asked: the reminder scheduler exists and enqueues delayed jobs, but nothing consumes the reminders queue yet. It's half-built, and I'd rather say that than have you find it."

11 · Close

"The through-line is that correctness properties are enforced at the lowest layer that can enforce them. Uniqueness is a database index, not a check-then-insert. Authorization is a domain rule, not a controller guard. Configuration is parsed once at boot and fails the deploy rather than the first request. Where I couldn't push a guarantee down a layer — like at-least-once notification delivery — I made the consequences idempotent instead."

Likely follow-ups, and the honest answers

QuestionAnswer
"Why the Redis lock if the index already guarantees it?"It doesn't add correctness — it reduces wasted transactions and gives a clearer error faster. I'd keep it, but I'd delete it before I'd delete the index.
"What if Redis dies?"Sessions and locks fail hard — everyone is logged out, and bookings fall back to index enforcement. Cache and idempotency degrade gracefully: the cache treats errors as a miss, and idempotency loses replay protection, which is a real correctness regression I'd want an alert on.
"Why Mongo for something this relational?"Fair challenge. Postgres with an exclusion constraint on a tstzrange would express the no-overlap invariant more directly and handle variable-length appointments, which the fixed-slot index doesn't. Mongo works because slots are a fixed grid — the constraint is equality on startsAt, not range overlap. If appointment lengths became variable, I'd move.
"How do both parties see updates?"Polling at 10 seconds. There's a GraphQL subscription in the code but it's not used in production — the in-process PubSub doesn't fan out across instances, Cloud Run bills for idle connections, and there's no session affinity. Making it work means Redis PubSub plus affinity. An appointment request isn't a chat message.
"What's the weakest part?"The worker co-location, and the missing request-id correlation. Also: no audit trail of who changed what, which for a clinical system is a real gap rather than a nice-to-have.

Open questions

Six things I could not determine from the codebase. I've flagged them rather than assuming, because each one changes what you'd say in an interview.

  1. How is the frontend deployed? Only the API has a Dockerfile and a Cloud Run service. There's no static hosting, CDN, or bucket configured, and no build output target. Is the SPA meant to be served by Cloud Storage + Cloud CDN, by Firebase Hosting, or from the API container itself? This also determines whether ALLOWED_ORIGINS: https://scheduler.example is same-origin with the API or genuinely cross-origin — which changes the CSRF story.
  2. Is the reminders queue intentionally unconsumed? ReminderScheduler enqueues delayed jobs with a deterministic jobId, but no Worker is opened for that queue and nothing calls schedule() from the appointment flow. Half-built and known, or an oversight?
  3. Who creates users? There's login, logout, and me, but no registration endpoint. Accounts exist only via migration 005's demo seed. Is registration out of scope, or admin-provisioned?
  4. Where do doctor and patient profile records come from? doctors, patients, and availability_rules are read by the app but nothing writes them outside tests — saveSchedule has no HTTP surface. Is schedule management deliberately deferred?
  5. Is the notification provider a real vendor? The URL defaults to https://notifications.example. If you have a specific one in mind (SendGrid, Twilio, Postmark), the retry semantics and the idempotency-header name would need checking against their actual API.
  6. Multi-doctor? The frontend hardcodes a fallback of doctor-1 and reads ?doctorId= from the query string; there's no doctor directory endpoint. Is single-clinic the intended scope, or is discovery just not built yet?
